3. Python的GIL是什么，异步编程里asyncio的事件循环怎么理解，FastAPI为什么适合写Agent服务
*Python的GIL是什么*
GIL 是“全局解释器锁”。
同一个进程里，同一时刻通常只有一个线程执行 Python 字节码。

所以，多线程对两类任务的效果不同：
- CPU 密集任务：比如大量纯 Python 计算，比如图片解析OCR,多线程通常无法充分利用多个 CPU 核心，可以考虑多进程。
- I/O 密集任务：比如请求模型接口、查询数据库、下载 S3 文件，等待 I/O 时通常会释放 GIL，多线程仍然有用。

*异步编程里asyncio的事件循环怎么理解*
asyncio 的事件循环跑在一个线程里，负责调度协程。async def 定义的是协程，await 是它把控制权交回去的地方。比如我调模型，执行到 await llm.ainvoke() 就先挂起，循环转去处理别的请求；模型结果回来，再从这行接着往下跑。
切换只发生在 await。两次 await 之间的代码是一口气跑完的，所以纯计算不能写在协程里空转。Agent 服务里大部分时间都在等模型、Redis、向量库，这些等待用 await 让出去，一个线程就能同时撑住很多个正在等的请求。

*FastAPI为什么适合写Agent服务*
因为 Agent 服务通常有几个特征，正好与 FastAPI 比较契合：
- 网络等待多：反复调用模型、数据库、检索和业务接口，适合用异步方式处理并发请求。
- 需要流式返回：通过 SSE 或 WebSocket 返回生成内容、工具执行状态和最终结果。
- 结构化数据多：Pydantic 方便定义请求、响应及工具参数，进行格式校验。
- 执行过程长：方便接入超时、异常处理和连接生命周期管理，但这些机制仍需要你实现。

4. Java侧你怎么把一个现有SpringBoot服务对接到大模型Agent，用哪种调用方式，同步还是异步
目前的方法：RestClient+读流转发。Java开一个请求线程，持续读取Python的返回，写给前端。
改进：可以用虚拟线程，让请求运行在虚拟线程上。
聊天请求量大后,考虑WebClient+流式相应，必要时使用WebFlux。优点是，当很多人同时等 Python 返回时，Java 可以用更少的系统线程维持这些连接，让其他接口也能正常处理请求。
传统线程：请求等待，系统线程也被占着。
虚拟线程：请求等待，通常可以让出系统线程。
WebFlux：请求挂起，数据就绪后由事件循环线程继续处理。

6. MySQL里有一张对话日志表，量大了查询慢，你会怎么建索引，哪些字段不适合建
设计思路是：等值过滤字段放前面，排序字段放后面。
```
PRIMARY KEY (id)  -- 根据消息 ID 查记录

INDEX (tenant_id, session_id, created_at, id)
-- 根据会话查聊天记录

INDEX (tenant_id, user_id, created_at, id)
-- 根据用户查最近记录
```
哪些字段不适合建索引:低区分度字段,大文本字段content,不参与过滤、关联、排序的字段,更新频繁且查询收益很小的字段


7. 意图识别你做过么，是完全丢给大模型做分类，还是规则加模型混合，各自利弊
做过，用的是规则加模型，不是每句话都丢给大模型。
用户一句话进来，先走规则，规则定不了再调模型。
句子里有「文案、润色、改写」就切到文案；有「洞察、人群画像、触达偏好」就切到洞察；同时有 Journey 和「生成、创建」就切到 Journey。
规则的好处是稳定、便宜、可以单测。改口和多轮续接不会被模型改判，也不用为了一句「好的」再打一次模型。坏处是新说法要补词，长尾句子盖不住。
完全丢给模型的好处是长尾说法不用维护词表。坏处是同样一句话两次结果可能不一样，多一次调用的延迟和费用，而且分类错了会进错链路。创建、保存这种动作不能只靠分类结果，前面还要有确认。所以模型只做规则覆盖不到的那一下。


8. LangChain里Chain和Agent的区别，为什么复杂场景不能直接用简单Chain
Chain 是程序提前安排步骤，Agent 是让模型在执行过程中，根据结果决定下一步。

9. RAG基础流程讲一下，文档切片大小怎么定，切片大了小了分别有什么问题
上传之后按文件类型抽出文本，再用递归切块。分隔符从大到小试：空行、标题、换行、句号，实在切不开才按字符切。默认一块大约 500 字，相邻两块重叠 50 字，避免一句话正好卡在边界上。向量写入 Milvus，关键词走 BM25。
切片大小看「一块能不能独立回答一个问题」

切大了，一块里会混进好几个主题。向量被这几个主题平均掉，该排前面的片段排不上去。送进模型的无关文字变多，引用也只能指到一大段，对不上原段落。

切小了，一块只剩半句话或一个步骤，看不到前一句的条件。召回条数变多，拼出来的上下文仍然是碎的。

11. ToolCalling里怎么约束大模型传参Pydantic模型校验够不够，还要做什么兜底
Pydantic 不够。它主要保证“参数格式符合定义”，不能保证“参数符合业务、用户有权限、执行不会产生重复副作用”。
 1. 工具定义：让模型尽量传对
 2. 业务校验：参数正确，不代表业务正确
 3. 权限校验：身份信息由服务端确定
 4. 参数错误：反馈给模型有限次修正
 5. 执行兜底：超时、限次，以及写操作幂等
 6. 结果兜底：以实际工具结果为准

9. Kafka在Agent系统里用来干什么，任务执行队列和事件总线的用法区别
它负责 Agent 和业务系统里那些不能在一次请求里做完的异步消息，而且只分两种。
一种是事件总线，同一条 topic 上有多个消费组，各组都收到一份。
比如，document.published 上，向量组和图抽取组各做各的。

另一种是任务队列，一条 topic 只有一个消费组，组里可以有多个线程抢着做，但同一条消息只做一次。
比如，journey-runs 开 4 个线程，是因为跑一条 Journey 要花时间，避免一个线程卡住整队。

10. RocketMQ和Kafka在Agent工具异步场景里怎么选
Agent 工具异步调用选 RocketMQ。
Agent 工具调用是一条命令：带 thread_id 和 tool_call_id，执行可能要几秒到几分钟，失败要延迟重试，最后要把结果送回同一次运行。RocketMQ 的延迟消息、分级重试、死信队列和按 key 顺序消费就是为这种任务准备的。工具失败后按 10 秒、30 秒、1 分钟再试，仍失败就进死信，不必自己造重试主题。
Kafka 强在高吞吐日志和按分区重放。你们现在的 Audience shard、Journey run、文档解析都是这种流量，所以那几条链路不该搬。用 Kafka 做工具调用，延迟重试和死信得自己做，请求和回复也要靠两个 topic 加关联 ID 拼出来。工具调用量远没到 Kafka 的吞吐优势有意义的程度。
