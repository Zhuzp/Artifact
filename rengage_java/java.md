**Java 基础与并发**
*1. HashMap 的原理是什么？线程安全吗？*
hashmap其实就和前端的map类似，通过get,put取值加值。但是hashmap是根据key算出一个位置，获取的时候用key获取那个位置的值，如果冲突了（也就是两个key算出同一个位置，就在这个位置上排成一串，后来的挂在前面的后面），取得时候根据key查到这个位置，然后发现第一个值不是要的key值，就看下一个。

*ConcurrentHashMap是什么？怎么保证线程安全？*
key不同的话，算出同一个位置，后来的会挂到先来的位置上。key相同的话，就会直接覆盖旧值。
如果两个线程同时用相同key修改，就会导致覆盖。ConcurrentHashMap就是A用key算出位置后，就把这个位置锁住。b只能等a放完，然后再往这个位置上挂或者覆盖。

*synchronized 和 ReentrantLock 有什么区别？*
```
synchronized (lock) {
    // 同一时刻只有一个线程能进来
}
```
```
lock.lock();
try {
    // 同一时刻只有一个线程能进来
} finally {
    lock.unlock();
}
```
synchronized写在一段代码上。A正在执行这段代码时，B要执行同一段就等着，A出来B再进。锁自动拿、自动放。
ReentrantLock就是类似于可配置版的synchronized，可以多做几件事：试锁、只等一段时间、按条件排队。unlock() 必须放在 finally 里，否则中间抛异常，锁就永远不放开，别人一直等。
 
*线程池参数和拒绝策略*
ThreadPoolExecutor 常见参数：
- corePoolSize：常驻的核心线程数。
- maximumPoolSize：最多允许的线程数。
- keepAliveTime：多出来的线程空闲多久后回收。
- workQueue：暂时处理不了的任务放在哪。
- threadFactory：如何创建线程，比如设置线程名。
- handler：线程和队列都满了时如何处理新任务。

重要的是线程池接收任务的顺序：
1. 核心线程没满：创建线程处理任务。
2. 核心线程已满：先尝试把任务放进队列。
3. 队列也满了：再创建非核心线程，直到最大线程数。
4. 线程数到上限且队列满：执行拒绝策略。
ps:队列满了后，新进的任务会先执行，在队列排队的队伍继续等。

常见拒绝策略：
- AbortPolicy：抛异常，明确告诉调用方任务没接收。适合不能悄悄丢任务的场景。
- CallerRunsPolicy：让提交任务的线程自己执行，降低提交速度，形成“反压”。
- DiscardPolicy：直接丢掉新任务。
- DiscardOldestPolicy：丢掉队列里最早的任务，再尝试接收新任务。

*线程状态、sleep 和 wait 的区别*
线程有哪些状态
- NEW:已创建，还没调用 start()
- RUNNABLE: 可运行：正在跑，或在就绪队列里等 CPU
- BLOCKED: 想进 synchronized，但锁被别的线程占着
- WAITING: 无限期等待，直到别的线程唤醒
- TIMED_WAITING: 带超时的等待，时间到了自己醒
- TERMINATED: run() 结束，线程退出

Thread.sleep(millis) 只是让当前线程歇一段固定时间。时间到了，或者被 interrupt，它回到 RUNNABLE。这段时间线程处于 TIMED_WAITING。

Object.wait() 是线程协作：当前线程在某个对象上等待条件成立。不带超时时进入 WAITING，带超时（wait(millis)）时进入 TIMED_WAITING。醒来要靠同一个对象上的 notify() / notifyAll()、超时，或者中断。

*死锁：怎么产生、怎么避免*
死锁是两个或多个线程互相拿着对方下一步才肯放的资源，谁都走不下去。
怎么避免
固定加锁顺序。 所有线程都按同一个全局顺序拿锁，环就组不起来。
拿不到就放弃，而不是一直等。 ReentrantLock.tryLock(timeout) 在时限内拿不到就释放已经持有的锁，退回去重试。

ThreadLocal 给每个线程准备一份自己的变量。线程池里的线程会被反复复用，这份变量会跟着线程留下来，所以用完必须 remove()。(有点类似useContext的作用)
- 和线程池冲突在哪里
普通线程跑完就没了，上面的 ThreadLocalMap 一起被回收。线程池里的工作线程一直活着，一个任务 set 进去的值，下一个任务 get 还能看到。
这会带来两件事：
1. 串数据。 请求 A 把用户放进 ThreadLocal，请求 B 分到同一条线程，读到的仍是 A 的用户。权限、租户、trace 都会错。

**Spring / Spring Boot**
*Spring 和 Spring Boot 的区别，自动配置原理*
Spring 容器只认 bean。数据源、MyBatis、Jackson、内嵌 Tomcat 都要你自己声明：引入哪些包、版本是否兼容、@Bean 怎么写、参数从哪来。项目能按你的方式拼，但每个新工程都要先把这套骨架搭一遍。
Spring Boot 把常见组合收成 starter，并在启动时按 classpath 和配置文件补上默认 bean。你仍然跑在 Spring 容器里，@Component、@Configuration、AOP、事务的语义都没变。少写的是那些每个项目都差不多的样板。

*Spring Bean 默认是单例，为什么不一定线程安全*
单例只保证容器里这一个对象被所有线程共用。线程安全取决于这个对象身上有没有会被同时改的状态。Spring 创建和发布这个单例时会做同步，方法被调用时不会替你加锁。

*一次请求怎样经过 Controller、Service、Mapper 到数据库？*
一次请求的路径是：HTTP 进来后，由 DispatcherServlet 找到 Controller，Controller 调用 Service，Service 在事务里调用 Mapper，Mapper 的代理对象通过 JDBC 执行 SQL，结果再原路返回成 JSON。

*Spring 的 IOC、DI 是什么？*
IoC 是控制反转。对象的创建和组装交给 Spring，不由业务类自己动手。
没有 Spring 时，LiveEventIndex 要自己把依赖造出来；这样每新建一个 LiveEventIndex，就要负责它用到的所有对象怎么来。Spring 接手之后，这些对象由它在启动时造好、存好，业务类只声明自己需要什么。

DI 是依赖注入，是 Spring 实现 IoC 的具体做法：对象需要的东西从外面传进来。
LiveEventIndex 的构造函数列出了它要用的 5 个对象。Spring 创建它时，把已经造好的那 5 个填进参数。
类上的 @Service 是在告诉 Spring：这个类归你管，请你造一个，并把它需要的参数注入进来。造出来、被 Spring 管着的那个对象，就叫 Bean。

*Spring AOP 怎么实现？有什么限制？*
AOP 就是把很多方法都要做的同一件事抽出来，单独写一次，自动套到这些方法外面。方法里面只留自己的业务。
比如创建画布、修改画布、发布画布，每个方法都要先开事务，成功就提交，失败就回滚。不抽出来的话，每个方法都得写一遍：
```
public JourneyDto create(...) {
    开启事务;
    try {
        // 真正创建画布
        提交;
    } catch (RuntimeException e) {
        回滚;
        throw e;
    }
}
```
AOP 的做法是这段开关事务的代码只写一处。方法上标一个 @Transactional，Spring 在调用它之前和之后自动把事务套上。create 里面就只剩创建画布本身。

*Bean 生命周期*
Bean 生命周期就是 Spring 管辖的那个对象，从造出来到应用关闭，中间经过的几步。

1. 创建。 Spring 看到 @Service，调用构造函数把它 new 出来。构造函数上的依赖，这时已经传进来了。
2. 初始化。 对象刚造好、还没开始接请求时，跑一次标了 @PostConstruct 的方法。AudienceService 在这里灌种子人群，FirebaseConfig 在这里读凭证、初始化 Firebase。整个生命周期只跑这一次。
3. 使用。 之后这个对象就放着。别的 Bean 需要它时，Spring 把同一个对象注入过去，不会再 new 一个。
4. 销毁。 应用关闭时，如果写了 @PreDestroy，再跑一次做清理，比如关掉连接。你们项目里基本没写这一步。
平时只要记住两个时机：构造函数负责接收依赖，@PostConstruct 负责对象就绪后只做一次的准备工作。

*@Transactional 原理、传播级别、隔离级别、回滚规则*
@Transactional 靠前面说的 AOP 替身工作。别人调用这个方法时，替身先向数据库开启事务，再执行你的方法。方法正常返回就提交。抛出运行时异常就回滚。其实就一件事：这个方法里改了几张表，要么一起保存，要么一起撤销。

传播级别：一个带着事务的方法，又调用了另一个带着事务的方法时，里面那个方法是加入外面这一次，还是自己另开一次。
默认是哪种？ REQUIRED。外面已经有事务就加入，没有就自己开一个。里面失败，外面已经做的修改一起撤销。
REQUIRED 和 REQUIRES_NEW 的差别？ REQUIRES_NEW 是里面自己另开一次，先保存。外面后面即使撤销，也撤不掉里面已经保存的内容。适合记一条不能跟着业务一起撤销的日志。

隔离级别：一个事务还没提交的修改，别的事务能看见多少。不写的话就用数据库自己的默认级别。你们用的 MySQL InnoDB 默认是 REPEATABLE_READ。

回滚规则：默认只在抛出 RuntimeException 和 Error 时回滚。IOException、SQLException 这种检查型异常，事务仍然会提交。

*为什么同类内部调用会导致事务失效*
同一个类里自己调用自己，事务为什么不生效？ 因为事务是替身加上去的。类里面写 this.create()，走的是原对象，没有经过替身，传播和回滚都不会发生。必须从别的 Bean 调过来才行。

*@Scheduled 多实例执行问题*
面试一般就问两句。多实例会怎样：每台各跑一遍，任务重复。怎么保证只执行一次：用数据库条件更新，或者用 Redis 分布式锁，先抢到的执行。抢到之后机器挂了，锁要有过期时间，否则这条任务会一直没人做。受众分发里的 claimJob 就带了过期时间，超时后别的实例可以再抢。

**MySQL 与 MyBatis**
*什么是索引？为什么能加快查询？*
索引类似于数据库表的目录。不建索引是，数据库可能要逐行找。建了索引（创建索引是数据库再旁边另存一份目录，建表时写的`INDEX idx_mail_due(status, next_attempt_at)`就是在建这份目录。目录里的每一条由两部分组成：你指定的那几列，再加上这行的主键），查找时就可以先在目录里找到对应的那几条，根据主键id再去表里找对应的行数据。


*如何排查慢 SQL？*
查看实际 SQL 和参数，用 EXPLAIN 检查索引、预计扫描行数、排序等，再结合数据分布和耗时验证。还要排查锁等待、返回数据过多、N+1 查询，以及应用连接池等待。

`INDEX(status, next_attempt_at)`

*事务隔离级别有哪些？*
先解释三个问题：
- 脏读： A 把画布名字改成「新名字」，还没提交。B 读到了「新名字」。A 随后回滚，这个名字从未真正保存过。B 读到的是一份不存在的数据。
- 不可重复读： B 读到名字是「旧名字」。A 改成「新名字」并提交了。B 在同一个事务里再读这一行，名字变成了「新名字」。两次读的都是已经提交的数据，但同一行的内容变了。
- 幻读： B 按 status = scheduled 查出 2 条画布。A 新插入一条定时画布并提交。B 用同样的条件再查，变成 3 条。原来的那两行没变，多出来的是符合条件的新行。

*什么是行锁？锁的就是一行吗？*
行锁是数据库自己的锁。事务里执行 SELECT ... FOR UPDATE 或 UPDATE 时，InnoDB 把那一行锁上，直到这个事务提交或回滚才放开。别人要改同一行，就停在那里等。
行锁要写在一个事务里面。事务不结束，锁就一直占着。单独执行一句查询，执行完就放开了，等于没锁住。
最常见的是把要改的那一行先查出来并锁上。
`SELECT ... FOR UPDATE`

*什么是死锁？怎么解决？*
死锁是两个事务互相等对方手里的锁，谁都交不出来，也就谁都等不到。
事务 A 已经锁住 mail-001，接下来要锁 mail-002。事务 B 已经锁住 mail-002，接下来要锁 mail-001。A 等 B 放开 mail-002，B 等 A 放开 mail-001，两边都停住。
Mysql存储引擎InnoDB会发现死锁。然后会回滚其中一个事务，通常是改动比较少的那一个，抛错。另一个事务拿到锁，继续做完并提交。Java这边要接住这个错误，把这个事务重新跑。

*乐观锁和 SELECT FOR UPDATE*
乐观锁先允许大家读取，更新时检查版本是否变化；悲观锁先锁住记录，再执行后续操作。乐观锁适合冲突不频繁、允许提示重试的场景；FOR UPDATE 适合需要串行保护同一条记录的场景。
乐观锁是更新的时候筛选带上id和当前版本，如果两个请求都拿着 revision=5，只有一个能成功更新成 6，另一个影响行数为 0。

*为什么需要数据库唯一约束*
唯一约束是数据库在插入时当场保证 这几列的组合只能有一行。唯一约束还可以加在别的列上，也可以是几列合在一起唯一。

*游标分页和普通分页的区别*
普通分页用页码跳。游标分页记住上一页最后一条的位置，从它后面继续拿。
普通分页缺点：OFFSET 很大时，数据库通常仍要扫描并跳过前面的记录，越往后成本越高。数据中途新增、删除，也可能使偏移位置变化，造成重复或遗漏。
游标分页缺点：不方便直接跳到第 100 页。排序需要稳定，如果排序字段不唯一，就要增加唯一字段作为第二排序条件。

*Mapper 和 Wrapper 分别是什么？*
Mapper 负责执行数据库操作，继承 BaseMapper 后可以使用常见增删改查方法；Wrapper 用来组合查询或更新条件。事务由 Spring 管理，它们本身不会自动把多次操作变成一个事务。

*两人同时编辑，冲突后为什么不能直接重试？*
两个人都拿到 revision 5，第一个人保存成功后变成 6，第二个人再拿 5 保存就会失败。

如果第二个人只把版本号换成 6，再提交原来的旧内容，仍然可能覆盖第一个人的修改。应该重新读取数据，再让用户确认、合并或重新编辑。

**JVM 基础**
*JVM 内存区域怎么划分？*
堆：new 出来的对象和数组都在这里。
栈是每个线程独有的，保存方法调用帧、局部变量和部分中间计算数据；
方法区：类的信息放这里，比如类名、方法定义、常量。Java 8 之后这块叫元空间（Metaspace），使用的是本机内存，不占堆的大小。

*垃圾回收怎么判断对象可以回收？*
没人还能从「正在用的地方」走到这个对象，它就可以回收。
正在用的地方主要是这些：
    某个还没结束的方法里的局部变量，比如栈上的 entity
    静态字段，比如某个类上一直放着的对象
    正在执行的方法本身用到的对象

*为什么堆分年轻代和老年代？*
大量对象是短命对象，所以 JVM 通常把新对象优先放在年轻代，经过若干次回收仍存活的对象可能晋升到老年代。年轻代回收通常比较频繁、耗时较短；老年代回收频率低，但单次可能更重。具体分区和策略会随 GC 收集器变化。

*GC 停顿是什么？*
某些 GC 阶段需要暂停部分或全部应用线程，暂停时间会影响请求延迟。排查时看 GC 日志中的回收频率、耗时、回收前后堆占用，以及是否出现长时间 Full GC，而不是只看 GC 次数。


*OOM 和内存泄漏*
- 内存泄漏：对象已经没有业务价值，但仍被引用，GC 无法回收，长期积累后可能 OOM。
- 内存溢出：JVM 申请不到需要的内存，抛出 OutOfMemoryError。原因可能是泄漏，也可能是瞬时对象过多、堆太小、元空间不足、直接内存耗尽等。

*线上 OOM 怎么排查？*
可以按这个顺序回答：
1. 先保留现场：确认错误类型、时间、实例和最近发布；检查是否已有 heap dump、GC 日志。heap dump 可能很大，要确认磁盘空间，避免直接在线上高峰生成导致额外停顿。
2. 看指标和日志：查看堆使用曲线、GC 频率与停顿、请求量、线程数、容器内存，判断是堆、元空间还是直接内存问题。
3. 分析 dump：用 Eclipse MAT、JProfiler 等查看大对象、数量异常的对象及 GC Roots 引用链，找出“谁还持有它”。
4. 修复并验证：检查静态集合、缓存无上限增长、监听器未注销、线程本地变量未清理、任务积压等；修复后用压测和监控确认占用趋于稳定。

*一个 Java 类怎么加载进 JVM？*
第一次用到这个类时，JVM 才去读它的 .class 文件，检查通过后放进方法区。不是程序一启动就把所有类都装进来。

比如第一次执行 new JourneyEntity()，会经过这三步：

 1. 找到文件并读进来。 类加载器按类名到依赖包或编译结果里找到 JourneyEntity.class，把里面的字节码读进方法区，同时生成一个 Class 对象，代表「这个类本身」。
 2. 检查并准备。 确认这份字节码没有被篡改、格式合法。然后给静态字段分配位置，先填默认值：数字是 0，对象是 null，布尔是 false。这时还没执行你写的 static int x = 1。
 3. 初始化。 先初始化父类，再执行这个类自己的静态字段赋值和 static { } 代码块。x 到这里才变成 1。做完就可以 new 对象了。

*常见线上问题排查*
1. CPU 高: 先确认实例、时间范围和流量是否异常；再通过线程栈找到高 CPU 线程，定位对应代码。常见原因有死循环、频繁重试、复杂计算或锁竞争。
2. 请求变慢: 看线程状态、线程池活跃数和队列长度，再检查是否有阻塞 IO、锁等待、下游变慢或任务提交速度超过处理速度。不能只靠增加线程数解决，可能会让数据库连接和 CPU 更紧张。
3. 频繁 Full GC: 看 Full GC 前后老年代占用是否下降。如果回收后仍很高，怀疑大量对象仍被引用；如果能明显下降但很快又升高，可能是分配速率过高或流量突增。结合 heap dump 和 GC 日志确认。
常用工具可以记这些：
- jcmd：查看 JVM 信息、生成 dump、执行诊断命令。
- jstack：查看线程栈。
- jmap：查看堆或生成 heap dump。
- GC 日志、APM、JFR：观察回收、请求链路和运行时行为。

**缓存问题**
*缓存穿透、击穿、雪崩是什么？怎么处理？*
1. 穿透：有人用一个不存在的事件名不停请求，比如 event_not_exist。缓存里没有这个 key，于是去查库；库里也没有，所以不能把结果写进缓存。下一个请求来了，还是没有 key，再查一次库。这个事件每来一次就查一次库。
处理是把「没有」也存下来。你们项目里查不到画布时，会往 Redis 写入一个空列表，30 秒内再来就直接返回，不再查库。
2. 击穿：order_created    有画布，缓存也在。它的 5 分钟到期了，这一秒刚好有几百个这种事件进来。大家都发现缓存没了，于是几百个请求一起去查库，查的是同一份数据。
处理是同一时间只放一个请求去查库，其他人等他查完。你们就是按事件名加锁，拿到锁之后再看一次缓存，避免白等
3. 雪崩：下午 3 点集中写进缓存的 key，过期时间都是 5 分钟，3 点 05 分一起失效。或者 Redis 进程挂了，所有 key 同时消失。接下来每一条请求都去查库，数据库被打满。
处理是让过期时间错开，比如 5 分钟再加一个 0 到 60 秒的随机数，不要在同一秒集体失效。Redis 用主从或集群，一台挂了还有别的节点。应用里还可以留一份很短的本地缓存，Redis 暂时连不上时先用它顶一下，同时把打到数据库的请求量限制住。

**Kafka**
*为什么用 Kafka 而不是 RabbitMQ？*
答：Kafka 吞吐量高、消息持久化、支持回放；RabbitMQ 更适合低延迟任务队列，你这个场景是事件流，Kafka 更合适

*Topic、Partition、Broker、Consumer Group 分别是什么？它们之间是什么关系？*
Topic 是一类消息的名字。Partition 是这个名字下面拆开的几条队列。Consumer Group 是一组一起消费这些队列的程序，组内同一条消息只处理一次。

Topic 就是消息的分类。你们有 rengage.user-events（用户事件）和 rengage.journey-runs（画布执行）。往哪个 Topic 发，就进哪一类。

Partition 是一个 Topic 里的分片。这两个 Topic 各拆成 8 片。一片里面的消息按先后顺序排。不同片可以同时被不同的程序读，所以才能并行。一条消息只进其中一片，通常用消息的 key 算出进哪一片。

Broker 就是一台正在运行的 Kafka 服务器。消息最终写在它的磁盘上，生产者也是连上它才把消息发出去，消费者也是连上它才把消息读出来。

Consumer Group 是消费这一类消息的一组程序，用 groupId 标识。组里的成员把 8 个分片分掉，每个分片同一时间只分给其中一个成员。所以组内不会两个人处理同一条消息。成员多于 8 个时，多出来的那个分不到片，闲着。

*Kafka 如何保证消息不丢失？*
- 生产者：acks=all，等所有副本写入才确认；retries 配置重试次数
- Broker：replication.factor >= 2，多副本存储；min.insync.replicas=2
- 消费者：手动提交 offset，处理完再提交；你项目里 enable.auto.commit:false 就是这个

*"Kafka 消费者挂了，消息会丢吗？"*
- 不会。offset 手动提交，挂掉前未提交的 offset 会在重启后重新消费
- 重启后同 group 内其他消费者或新实例会触发 Rebalance，接管对应 partition

*消费处理与 offset 提交的先后顺序。*
通常先处理业务，成功后再提交。

先提交再处理，进程崩溃可能导致业务没做，但进度已经过去了。

先处理再提交，崩溃后可能重复处理，所以要配合幂等。Spring Kafka 具体什么时候提交，要看实际配置。

*数据库写成功但消息发送失败怎么办？了解 outbox 方案。*
可以用前面说的 outbox：业务数据和待发消息一起写入数据库事务，再由后台不断投递。

投递仍可能重复，所以消费端还是要幂等。它解决的是“消息不会因为提交后的进程崩溃而直接消失”。

*什么是 Rebalance？会带来什么影响？*
消费者加入、退出，或者被认为失去响应时，Kafka 会重新分配分区。

它可能带来短暂停顿，也可能让未及时提交进度的消息再次处理，所以消费者要考虑重复执行。

*至少一次、至多一次、恰好一次分别是什么？*
这三句话说的是消息会不会丢、会不会重复。Kafka 默认更接近至少一次；恰好一次只覆盖「从 Kafka 读出来、处理完、再写回 Kafka」这条链路。

至多一次。 每条消息最多被处理一次，允许丢失，不会重复。生产者发出去就不重试。消费者先提交 offset，再处理消息。进程如果在提交之后、处理之前宕掉，这条消息不会再被投递。

至少一次。 每条消息至少被处理一次，不会丢，但可能重复。生产者开启重试，并等 broker 确认写入（acks=all）。消费者先处理完，再提交 offset。处理成功后、提交前宕掉，恢复时会把同一条再投递一次。业务侧要用幂等把重复消化掉，例如用消息 id 去重。

恰好一次。 在 Kafka 内部的「消费 → 处理 → 再写入 Kafka」链路里，结果只生效一次。靠两样东西实现：

幂等生产者：给每个生产者分配 PID 和递增序号，broker 丢掉重试造成的重复。
事务：消费位移的提交和下游写入放在同一个事务里，一起成功或一起失败。下游消费者用 read_committed，读不到未提交的消息。

*重复消费、消费幂等、失败重试、死信、任务恢复。*
让同一条业务消息执行多次，最终业务结果仍然一致。
常见做法是：业务唯一键、数据库唯一约束、带条件的状态更新，并把相关数据库操作放进事务。
不能只做“先查询有没有，再插入”，因为多个消费者可能同时查到“没有”。

重试：暂时失败后再试，比如下游超时。

死信：超过重试次数，或者无法正常处理的消息，转到专门位置，方便排查和人工处理。

任务恢复：服务重启后，根据数据库保存的任务状态和检查点，继续未完成任务。

重试要有限制，并增加等待时间，不能失败后不停立即重试。

*消费积压如何定位？任务太慢如何拆分？*
先看消息进入速度和消费速度，再看下游接口、SQL、失败重试、线程池是否拖慢处理。
大任务可以按收件人范围或 ID 分片，记录每片进度，失败只重试对应分片。
加消费者不一定有效：可能分区不够，也可能真正瓶颈是数据库或邮件供应商。

*消费者数量超过 Partition 数量会怎样？*
同一消费组中，多出来的消费者拿不到分区，会空闲。增加消费者数量不一定提高吞吐，还要看分区数和实际瓶颈。

Spring是什么？
Spring 是一个 Java 开发框架，主要帮我们管理对象，以及对象之间的依赖关系。
比如 Controller 需要调用 Service，以前需要自己创建 Service 对象；使用 Spring 后，可以把对象交给 Spring 容器创建和管理，再由它把 Service 注入到 Controller 中，这就是 IoC 和依赖注入。
此外，Spring 还提供 AOP 和事务管理等功能，方便统一处理日志、事务这些公共逻辑。

Spring boot是什么?
Spring Boot 是基于 Spring 的开发框架，主要作用是简化项目搭建和配置。
比如以前搭建一个 Web 项目，需要自己引入依赖、配置服务器和各种组件。Spring Boot 提供 starter 和自动配置，引入相关依赖后，它会根据依赖和配置，自动配置很多常用组件。初始化时他会扫描包里的类，带有@Component类似注解的就会注册到容器里，以key->value的方式存着，key是类名，value是实例，后面Controller想要用到Service，就去容器里找对应的类。

Spring Security + JWT？
登录成功 → 拿到 JWT → 带着 JWT 请求删除接口 → Spring Security 校验 JWT，并检查有没有删除权限 → 通过才执行删除。

双 Token 机制？
双 Token 机制使用短期的 Access Token 访问接口，使用长期的 Refresh Token 续期。Access Token 过期后，客户端调用刷新接口，后端校验 Refresh Token 并签发新的 Token；如果 Refresh Token 也失效，用户就需要重新登录。
