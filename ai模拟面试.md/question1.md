### 逐点评价

**第 1、2 点：基本合格**

链路比较完整，尤其是：

```text
S3 -> 数据库 -> Kafka -> Python 解析 -> 审核 -> 分块/向量化 -> pgvector + ES -> 问答
```

面试时注意把“解析”和“索引”分开说，并明确状态变化，例如：

```text
UPLOADED -> PARSING -> PENDING_REVIEW
-> INDEXING -> AVAILABLE
```

另外，“AI 服务端去 S3 拉文件”可以说成“Python 消费 Kafka 后根据对象 key 下载源文件”，会更准确。

**第 3 点：太简单**

不要只说“Java 负责业务，Python 负责 AI”。可以说：

> Java 服务负责用户、租户、文档元数据、审核状态、权限和对外业务接口；Python 服务负责文档解析、切块、Embedding、混合检索和 Agent 工作流。两边通过 Kafka 传递解析和索引事件，S3 传输文件，数据库保存任务状态。

**第 4 点：需要更具体**

你可以这样说：

> 我主要负责知识库文件从上传后的异步解析，到审核后的切块、向量化、pgvector 和 Elasticsearch 写入这一整条链路；同时参与了 LangGraph 工作流中的节点设计和状态流转。Java 侧的业务接口和状态管理不是我独立负责的，但我负责和它定义事件字段、状态以及失败重试时的协作方式。

这里要诚实区分“负责”和“参与”。另外面试中不要说“lnaggraph”，要说 **LangGraph**。

### 第 5 题：最难的问题怎么回答

你现在说“不知道”，会让面试官怀疑项目深度。你不需要编造线上事故，可以用实际设计难点回答：

> 我认为最难的是文档索引链路的异步一致性。因为 PGVector 和 Elasticsearch 是两个独立存储，不能用一个本地事务保证同时成功。如果向量写入成功、ES 写入失败，直接重试会造成重复写入。
>
> 我的处理思路是给每次索引生成 `event_id`，给每个文档维护 `document_id + version`，PGVector 的分块使用 `document_id、version、chunk_id` 做唯一约束，ES 使用同样的业务组合生成稳定文档 ID。这样重复消费时，PGVector 可以跳过已存在的分块，ES 使用幂等写入覆盖原文档。
>
> 任务状态会记录解析、向量写入、ES 写入和整体完成状态。Python 服务重启后根据状态继续未完成步骤，Java 收到完成消息时还要校验文档版本，避免旧版本任务覆盖新版本。

这段回答的价值在于：它体现了你理解**分布式任务、幂等、版本隔离和最终一致性**，不要求你声称已经实现了所有高级机制。

如果项目当时没有真正实现，可以说：

> 当前项目中已经实现了基础状态流转和重复写入控制；更完整的任务状态表、死信队列和自动补偿是我认为下一步需要完善的部分。

### 第 6 题：没有指标怎么办

不要虚构并发量和准确率。可以分成“当前已有指标”和“上线后应该监控的指标”：

> 当前项目还没有完整的大规模线上指标，我主要通过链路日志和任务状态判断处理是否成功。生产化后我会重点补充四类指标：
>
> - 稳定性：解析成功率、索引成功率、Kafka 消费失败数、重试次数；
> - 性能：文件解析耗时、Embedding 耗时、检索 P95 延迟、端到端响应时间；
> - 效果：Recall@K、MRR、Rerank 后命中率、答案引用准确率；
> - 成本：单次请求 Token 数、Embedding 调用量和模型费用。
>
> 同时用 `request_id` 或 `trace_id` 串起 Java、Kafka、Python、检索和模型调用，方便定位问题。

这比直接说“不知道”强很多，而且没有冒充已有成果。

### 你这题可以组织成这样的完整回答

> 这个项目主要拓展了 Rengage 的 AI 能力，包括通过 Emma 对话生成营销文案、根据自然语言生成 Journey、分析人群特征，以及基于企业知识库回答问题。
>
> 知识库链路是：文件上传后，Java 服务保存元数据并将源文件放入 S3，然后通过 Kafka 发送解析事件。Python 服务消费事件，根据对象 key 从 S3 下载文件，按文件类型选择 Parser，转换为 Markdown，再把解析产物存回 S3，并更新解析状态。运营审核通过后，Java 发送索引事件，Python 对文档切块、生成 Embedding，同时写入 pgvector 和 Elasticsearch，完成后发送索引完成事件，Java 更新文档为可用状态。
>
> 问答时，系统先识别用户意图，再根据需要调用人群查询等工具，然后对知识库进行向量和关键词双路召回，使用 RRF 合并、Rerank 后，将相关片段交给模型生成回答。
>
> Java 主要负责业务、权限、文档状态和对外接口，Python 负责解析、索引、检索和 AI 工作流。我主要负责文件解析到分块、向量化、pgvector 和 Elasticsearch 写入的链路，也参与了 LangGraph 状态流转和部分节点开发。
>
> 我认为最难的是 PGVector 和 ES 的最终一致性。我的方案是用 event_id 标识一次任务，用 document_id 和 version 隔离版本，用 document_id、version、chunk_id 防止向量重复，用稳定的 ES 文档 ID 做幂等写入，并在完成消息中校验版本，避免旧任务覆盖新版本。
>
> 当前项目还没有完整的大规模线上指标。生产化后我会通过成功率、失败重试、处理耗时、检索 P95、Recall@K、MRR、Token 成本和 Trace 来评估稳定性、效果和成本。
