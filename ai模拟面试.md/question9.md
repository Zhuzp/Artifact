
**下一题：AI 应用评测**

如果公司问你：“如何证明这个知识库问答系统比以前更好？”请回答：

1. 你如何构造评测数据集？
2. 如何评价召回效果？
3. 如何评价最终答案质量？
4. 如何发现幻觉？
5. Prompt 或模型更换后，如何防止效果变差？
6. 如何同时监控质量、延迟和成本？

*ai answer*
你的理解方向是对的，但面试中不要只说“让 AI 看差多少”。要把评测拆成两层：

```text
检索评测：找没找到正确 Chunk
生成评测：基于找到的 Chunk，答案是否正确、完整、有依据
```

### 一、先构造评测集

从已经解析好的文档中抽取一部分，人工或半自动建立数据集：

```json
{
  "question": "退款申请需要哪些材料？",
  "expected_chunk_ids": ["doc1_v1_chunk_03", "doc1_v1_chunk_04"],
  "reference_answer": "需要提交订单号、付款凭证和退款原因。",
  "must_cite": true
}
```

建议包含几种问题：

- 原文明确出现答案的问题；
- 同义表达和口语化问题；
- 需要跨多个 Chunk 综合的问题；
- 产品编号、合同编号、错误码等精确匹配问题；
- 文档中没有答案的问题；
- 有权限和无权限的问题；
- 新旧版本容易混淆的问题。

最开始不需要几千条，可以先做：

```text
50-100 条问题
20% 精确关键词
40% 语义问题
20% 多 Chunk 问题
20% 无答案或权限问题
```

如果没有人工数据，可以先用 LLM 根据文档生成问题和标准答案，再人工抽查。面试时要说明：**自动生成的数据必须人工抽样校验，否则评测集本身可能不可靠。**

### 二、评估检索效果

检索阶段只看系统有没有找对 Chunk，不看最终答案。

常用指标：

```text
Recall@K
Precision@K
MRR
nDCG
```

例如 `Recall@5`：

```text
前 5 个召回结果中包含任意正确 Chunk 的问题数
/
问题总数
```

你还可以记录：

```text
向量检索命中率
BM25 命中率
RRF 后命中率
Rerank 后命中率
```

这样可以知道问题出在：

- 向量模型；
- BM25；
- RRF 参数；
- Rerank；
- 权限过滤；
- Chunk 切分。

### 三、评估最终答案

至少看四个维度：

- **正确性**：和标准答案是否一致；
- **相关性**：有没有回答用户真正的问题；
- **完整性**：是否遗漏关键点；
- **依据性**：答案是否能被检索到的 Chunk 支持。

可以让模型做初步评分，但不能完全依赖模型。建议：

```text
自动评测全部数据
人工抽查 10%-20%
重点检查低分样本和高风险问题
```

如果系统要求引用来源，还可以检查：

```text
引用的 Chunk 是否真的支持答案
是否引用了无权限文档
是否引用了旧版本
```

### 四、怎么发现幻觉

可以设计两类检查：

**答案有依据性**

把答案中的事实拆成若干陈述，逐条检查是否能从上下文中推出。如果上下文没有依据，就标记为可能幻觉。

**无答案问题**

评测集中故意加入“文档没有答案”的问题，检查模型是否会诚实回答：

```text
当前知识库没有找到相关信息
```

而不是编造内容。

线上也要记录：

```text
问题
召回 Chunk
最终答案
引用来源
模型版本
Prompt 版本
```

这样出现错误时才能回放。

### 五、Prompt 或模型换版本怎么办

每次变更都记录：

```text
model_name
model_version
prompt_version
embedding_model
rerank_model
chunk_strategy_version
```

然后用同一套固定评测集跑回归：

```text
旧版本 vs 新版本
```

例如：

```text
Recall@5：0.82 -> 0.87
答案正确率：0.76 -> 0.80
幻觉率：0.11 -> 0.08
平均延迟：1.4s -> 1.8s
单次成本：0.03 元 -> 0.05 元
```

如果质量提升，但延迟或成本超出阈值，就不能直接上线。

### 六、质量、延迟、成本一起监控

请求级别记录：

```text
trace_id
tenant_id
question
检索耗时
Rerank 耗时
模型耗时
输入 Token
输出 Token
模型费用
召回数量
最终引用数量
错误类型
```

指标可以分为：

```text
质量：Recall@K、答案正确率、引用准确率、幻觉率
性能：P50/P95 延迟、各节点耗时
稳定性：失败率、超时率、重试次数
成本：单请求 Token、Embedding 次数、模型费用
```

### 面试中应该怎么说

你现在还没有接入完整评测系统，所以不要说“已经完成”。可以这样回答：

> 当前项目已经实现了 RAG 的检索和生成链路，但还没有接入完整的自动评测平台。我的设计是先从已解析文档中构建一套带标准答案和正确 Chunk ID 的评测集，分别评估检索和生成。检索侧使用 Recall@K、MRR、nDCG，比较向量召回、BM25、RRF 和 Rerank 各阶段的效果；生成侧评估答案正确性、相关性、完整性和引用依据，并加入无答案问题来观察幻觉和拒答能力。模型或 Prompt 变更时，用固定评测集做回归，同时记录模型版本、Prompt 版本、Embedding 版本和 Chunk 策略。线上通过 Trace 记录检索耗时、模型耗时、Token 成本、引用来源和错误类型，再结合人工抽查校准自动评分。

如果面试官追问“你实际做过吗”，直接说：

> 这部分目前还处于设计和准备接入阶段，线上已经有 LangSmith/LangFuse 的调用链路和 Token 记录，但还没有完整的 Recall、幻觉率和自动回归指标。这是我认为下一步需要补齐的生产化能力。

这个回答比把设计方案说成已经落地更可信。
