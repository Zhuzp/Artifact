假设 Java 消费 Python 发来的 `INDEX_COMPLETED` 消息时，更新 MySQL 失败了。

2. 如果一直失败，如何避免这个分区被一条坏消息永久阻塞？
3. 重试队列和死信队列分别解决什么问题？
4. 什么情况下可以提交 offset 并把消息标记为业务失败？

### 需要补充的细节

**1. offset 提交时机**

你的回答正确。只有在以下情况才提交原 Kafka 消息的 offset：

- MySQL 更新成功；
- 消息已经被安全转发到重试 Topic；
- 消息已经被安全转发到死信 Topic。

如果只是“准备重试”但还没写入重试 Topic，就不能提交原消息 offset，否则消息可能丢失。

**2. 死信是什么**

死信队列通常叫 **DLQ，Dead Letter Queue**，在 Kafka 里一般就是一个专门的 Topic，例如：

```text
document-index-completed
document-index-completed.retry
document-index-completed.dlq
```

它不是“消息消失的地方”，而是：

> 暂时无法自动处理、需要人工排查或后续补偿的消息存放处。

死信消息应该保留原始信息和失败上下文：

```text
原始 payload
event_id
document_id
version
失败次数
最后错误类型
最后错误信息
第一次失败时间
最后失败时间
```

**3. 为什么不能一直在主 Topic 重试**

如果一条坏消息一直留在分区头部：

```text
坏消息 -> 一直失败
后面的正常消息 -> 一直无法消费
```

这叫“毒消息”阻塞分区。把它转到延迟重试 Topic 或 DLQ，并提交原消息 offset，主 Topic 才能继续处理后面的消息。

**4. 你的第 4 点还需要分类**

不是所有达到最大重试次数的消息都应该直接当成业务失败。更准确的分类是：

- 数据本身错误：格式不支持、字段缺失、版本不存在，进入失败或 DLQ；
- 临时基础设施错误：数据库连接失败、Kafka 超时，继续重试或告警；
- 消息已经处理过：视为成功，提交 offset；
- 达到重试上限：转 DLQ，提交原消息 offset，等待人工或补偿任务。

面试中可以这样完整回答：

> Java 消费消息后先执行业务更新，成功后手动提交 offset。发生可重试错误时，将消息投递到带延迟策略的重试 Topic，确认重试消息写入成功后再提交原消息 offset。达到最大次数仍失败，或者确认是不可恢复的数据错误，就把原始消息、event_id、重试次数和错误信息写入 DLQ，再提交原消息 offset，避免毒消息阻塞分区。DLQ 后续由监控告警和人工补偿处理。

还有一个高级细节：如果你使用 Kafka Consumer 的手动提交，最好关闭自动提交：

```text
enable.auto.commit=false
```

并避免在同一个分区内并发处理导致 offset 越过尚未完成的消息。
