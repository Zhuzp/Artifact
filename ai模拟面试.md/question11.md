### 逐点补充

**1. 权限过滤**

完全正确。权限必须进入向量检索和 Elasticsearch 查询条件，不能先召回再过滤。

另外还要同时过滤：

```text
tenant_id
current_version
document_status = AVAILABLE
```

否则可能召回旧版本或尚未审核通过的内容。

**2. 上下文组成**

你列的内容基本完整：

```text
系统规则
用户问题
检索结果
必要的历史会话
```

历史会话不能无限全部传入，需要做：

- 截断；
- 摘要；
- 只保留和当前问题相关的历史；
- 防止历史内容覆盖当前权限和系统规则。

检索内容建议使用明确的数据边界，例如：

```text
<retrieved_context>
<context id="chunk_001" source="制度文档" page="3">
...
</context>
</retrieved_context>
```

**3、4. 防止幻觉和拒答**

你的思路正确，但 Prompt 约束不是唯一防线。还要：

- 传入的内容标记为不可信资料，不允许其中的文字改变系统规则；
- 要求模型回答时绑定引用的 Chunk ID；
- 后端校验引用的 Chunk 是否真的属于本次检索结果；
- 对低召回分数或上下文不足的情况直接走拒答策略；
- 把“知识库没有答案”和“系统出错”区分开。

可以要求模型输出结构化结果：

```json
{
  "answer": "...",
  "has_enough_evidence": true,
  "citations": ["chunk_001", "chunk_004"]
}
```

**5. 引用**

你的做法是对的。更可靠的方式是：

```text
Chunk 保存 document_id、version、page_number、section、chunk_id
-> 模型只输出 chunk_id
-> 后端根据 chunk_id 生成文档名和页码
```

不要让模型直接自由填写文档名和页码，否则可能出现虚假引用。

**6. 内容矛盾**

你回答的“指出冲突，不能强行统一”是正确的。还可以增加来源优先级：

```text
当前有效版本
-> 官方制度
-> 业务配置
-> 普通说明文档
```

如果冲突仍然存在，就展示双方来源、时间和页码，并要求用户确认。

面试中可以这样总结：

> 权限、租户、版本和审核状态在召回阶段过滤。传给模型的上下文包含结构化的 Chunk ID、文档名、版本、页码和内容，模型只能基于这些上下文回答，证据不足时拒答。模型输出引用 ID，后端根据真实检索结果生成最终引用，避免模型伪造来源。遇到内容冲突时展示不同来源和时间，不强行生成唯一结论。
